# Decisions

Append-only. One line per decision: `- YYYY-MM-DD: decision (why)`.

- 2026-10-27: Distribute as a Claude Code plugin + a template installed by `/odoo-harness:init` (shared logic updated in one place, project state stays in the project repo).
- 2026-10-27: One branch per Odoo version (17.0 → 20.0); shared harness changes land on 17.0 and are forward-ported.
- 2026-10-27: Docker Compose runtime with a disposable test DB (`dbfilter` locks the server to it).
- 2026-10-27: Instruction files in English; README and docs in English and French.
- 2026-10-27: No /session-start or /session-end commands; session start and end are automatic (hooks).
- 2026-10-27: Lint with pylint-odoo; e2e with Playwright.
- 2026-10-27: The template installer is a deterministic Python script; it never overwrites state files and merges CLAUDE.md, settings.json and .gitignore.
- 2026-10-27: Red-pen catalog is a Python module (`harness/errors.py`), not errors.yaml: no PyYAML needed on the host, and raw-string regexes are easy for agents to extend.
- 2026-10-27: Verification logic in Python (`harness/verify.py`, standard library only); `harness/verify.sh` is a thin wrapper.
- 2026-10-27: pylint-odoo and Playwright run in pinned containers (compose profile `tools`: `lint`, `e2e`), so every machine lints and tests the same way.
- 2026-10-27: The OCA-only rules manifest-required-author and missing-readme are disabled on the pylint command line (an rc-file `enable=odoolint` overrides any rc-file `disable`).
- 2026-10-27: Evidence integrity by fingerprint (sha256 of id + behavior + verification); changing a passing feature breaks `feature.py check`. `harness/evidence/` is write-denied to the agent.
- 2026-10-27: A feature's verification must include its own e2e test; zero Odoo tests or zero e2e tests count as a failure.
- 2026-10-27: Full e2e suite runs on the baseline, and on a feature verify when the change touches more than one module or shared files (anything outside one module, its e2e test files and docs).
- 2026-10-27: The fresh-DB install (L3) runs on `feature.py verify` only, not on the baseline, to keep `init.sh` fast.
- 2026-10-27: Hooks live in the plugin and stay thin: they call the project's harness scripts (static_checks.py, feature.py check, init.sh --check) and do nothing in projects without the harness.
- 2026-10-27: The Stop gate runs at the end of every turn, so it only blocks for an unclean state: static findings, broken feature list, or module/e2e code changed this session while PROGRESS.md (outside "Current state") is unchanged. With stop_hook_active it lets the turn end and records the problems in PROGRESS.md "Known issues" (no infinite loop).
- 2026-10-27: Odoo core/enterprise detection: an ancestor with odoo-bin, or a module whose manifest author is "Odoo S.A." or license OEEL; extra paths via PROTECTED_PATHS in harness.env.
- 2026-10-27: The Bash guard parses commands with shlex (quote-aware); a command mentioning feature_list.json or harness/evidence/ must be read-only or harness/feature.py; unparsable ones are denied.
- 2026-10-27: Commands on any database other than TEST_DB (and its _fresh twin), docker volume deletion and `git commit --no-verify` are denied.
- 2026-10-27: The odoo skill is written per version branch from the real odoo/odoo source of that version (20.0 first, then adapted to 19.0, 18.0, 17.0). tools/odoo-skill-extract extracts version facts (API exports, field types, view RNG, security format, route types, OWL exports, upgrade_code steps, deprecations) and check_skill.py fails CI if a reference uses API that does not exist in the branch's version.
- 2026-10-27: Shared harness files stay identical on all branches by being version-aware (ODOO_VERSION): security CSV format (ir.access from 20.0), odoo-version-api rules with version ranges, model-access check. Only odoo_version.json and skills/odoo/ differ per branch (merge=ours in .gitattributes).
- 2026-10-27: Every code example of a branch's skill must pass the harness odoo-version-api rules for that version (test), so the skill never teaches what the harness rejects.
- 2026-10-27: The e2e login presses Enter in the password field instead of clicking the first submit button (Odoo 20.0's login page has several).
- 2026-10-27: One marketplace on main, one plugin per Odoo version (odoo-harness-17 ... -20), each pinned to its branch with ref, so projects of different versions can use the harness on the same machine. plugin.json is per branch (entry name must equal manifest name).
- 2026-10-27: Projects pin the marketplace to ref main (the repository default branch could not be changed from this environment).
- 2026-10-27: init is a skill with disable-model-invocation (commands/ is the older plugin format); only the user starts initialization.
- 2026-10-27: The review -> check loop is a skill (add-harness-check) plus a read-only odoo-reviewer agent that proposes checks for new kinds of mistakes.
- 2026-10-27: CI runs the harness against real Odoo, PostgreSQL and Playwright in Docker on every version branch (tools/make_demo_project.py + odoo-e2e job), including an injected bug that must fail verification with a red-pen message and no unknown error.
- 2026-10-27: Odoo listens on 0.0.0.0 inside the container (Odoo 20.0 defaults to 127.0.0.1); the host port is published on 127.0.0.1 only.
- 2026-10-27: The e2e test DB persists between runs; e2e tests name what they create with the unique fixture.
- 2026-10-27: Red pens always show a short excerpt of the failing record (the assertion message), and the Odoo test summary record is not reported as a separate error.
- 2026-10-27: plugin.json has no version: Claude Code then versions the plugin by the commit of its branch, so pushes reach users (a pinned version keeps everyone on the cached copy).
- 2026-10-27: Projects turn on autoUpdate for the odoo-harness marketplace (third-party marketplaces do not auto-update by default).
- 2026-10-27: Installed files have an owner: state (never overwritten), project (created once, kept by --update which reports template changes as kept*), harness (replaced by --update), merged (CLAUDE.md block, settings, .gitignore). The update skill runs install_template.py --update; a different Odoo version is refused as a migration.
- 2026-10-27: The red-pen catalog is split: harness/errors.py (harness, updated) and harness/errors_project.py (project patterns, checked first, never overwritten).
- 2026-10-27: Deny rules use Edit(...) only: Claude Code matches Edit rules for every file-editing tool and ignores Write(...) rules (seen in a live session); the PreToolUse guard still covers Write and Bash.
- 2026-10-27: Phase 6 loop is a small explicit maker-checker graph (harness/loop.py, stdlib only) rather than a framework: the maker is claude -p, the judge is feature.py verify (plus the odoo-reviewer agent with --review), only verified work is committed, failed work goes to a named git stash and the feature is blocked. Default one feature per run so a human reviews each one.
- 2026-10-27: Odoo 17-19 test summary records logged at ERROR ("Module x: n failures...", "At least one test failed...") are not separate red pens (found by the odoo-e2e CI assertion).
- 2026-10-27: The loop's verify reopens a feature the maker already set to passing and verifies it again: the loop's own verify is the judge, whatever the maker ran (found in a live run).
- 2026-10-27: The Stop gate only counts code changed during the session: files already dirty at SessionStart (hashed in .harness/session.json) are ignored while unchanged, so a reviewer session opened on the maker's uncommitted work is not blocked (found in a live run).
- 2026-10-27: Marketplace plugin entries use url sources over HTTPS, not github sources: Claude Code clones github sources over SSH when an SSH key looks configured, and the install failed with 'Permission denied (publickey)' on a user's machine. The main CI rejects any other source type.
- 2026-10-27: The harness covers a whole Odoo project, not a module list: the layout is detected (scripts/detect_project.py) from the project's own Odoo config (addons_path), Dockerfile, git remote and branches, modelled on the fogits projects on gitlab.fogits.com (extra-addons/<client>, extra-addons/oca, ../enterprise, odoo-main/stag.conf, docker_compose_main/stag.yml, T<code> branches, staging -> main).
- 2026-10-27: The test runtime is the harness's own compose project (harness/docker-compose.yml, harness/odoo.conf): the project's image built from its Dockerfile, the repository mounted read-only, ../enterprise mounted read-only, its own Postgres and port 18069, a fresh test database with demo data; the dev stack (psql_<client>, 8069) is never used.
- 2026-10-27: Verify tests the changed modules and every custom module that depends on them (manifest depends graph); the baseline updates every custom module, and a baseline with no tests passes (legacy projects).
- 2026-10-27: Older findings are debt, not blockers: breaking findings (syntax, XML, manifest, security CSV) always block; project checks and pylint block only on lines changed on the branch; static_checks.py --all reports the rest (ratchet: touched lines must be clean).
- 2026-10-27: pylint runs with the project's .pylintrc-mandatory (OCA template), with --valid-odoo-versions from the project and unknown-option-value silenced (the fogits rcfile still enables messages removed from pylint-odoo 10 and validates Odoo 17.0 on 18/19/20 projects).
- 2026-10-27: Manifest versions follow what Odoo accepts ('1.0' is prefixed to '18.0.1.0'); only a version of another Odoo series or a non-numeric one is flagged (54 of 66 conforama modules would otherwise be false positives).
- 2026-10-27: New project check no-hardcoded-secrets: born from discovery, a GitHub token committed in the dev launcher of every fogits project; findings never print the value.
- 2026-10-27: An Odoo task (T<code>) groups one or more features (optional 'task' field); start checks out the task branch, created from the base branch only from a commit that has the harness; commits are '[T<code>] F-xxx behavior'; harness/gitlab.py mr pushes the branch and opens the merge request to staging once every feature passes (GITLAB_TOKEN from the environment or .env, never committed). The guard denies pushes to staging/main and destructive pushes.
- 2026-10-27: Third-party addons, the Enterprise checkout and deployment files (Dockerfile, compose files, odoo-*.conf, .gitlab-ci.yml, docker-compose/) are read-only for the agent: a human changes them.
- 2026-10-27: Odoo tasks are read through the client's Odoo MCP connector during discovery, read-only; without a connector the user pastes them.
- 2026-10-27: Claude Code can run in the client workspace (~/Project/<client>) as well as in the repository: the hooks find the harness in git/ (or the only child folder that has one), relative tool paths resolve against the launch folder, and the guard reads `git/harness/feature.py` and `git -C <dir>` commands. The harness and its state stay in the repository; the workspace only gets a generated CLAUDE.md importing git/CLAUDE.md and a .claude/settings.json with the same permissions rooted at git/ (not versioned; `--workspace-only` writes them after a fresh clone). Without them SessionStart injects git/CLAUDE.md itself.
- 2026-10-28: The `branches` CI job fails only on pushes to version branches and warns everywhere else (pull requests, work branches) (a PR that changes a shared file always differs from every branch until it is merged and forward-ported).
- 2026-10-28: User guide of a completed task (/guide T<code>, harness/guide.py): a French PDF for developers in docs/guides/, only for a task whose features all pass with valid evidence and are committed (checked by the script, not the prompt). Screenshots come from replaying the features' e2e tests with the harness_guide pytest plugin (guide.step captions), loaded by verify too so tests can use the fixture; the Odoo UI stays in the tests' language because locators use English labels. Claude writes only the text, in content.json; the PDF is printed by Chromium in the e2e container.
- 2026-10-29: One plugin, `odoo-harness`, installed once per machine, replaces the four per-version plugins (`odoo-harness-17`...`-20`). The Odoo version is data (`versions.json`, `ODOO_VERSION` in harness.env, `skills/odoo/versions/<version>/`), and CI runs every job once per version. The engine (`engine/`) is no longer copied into projects: the `odoo-harness` command runs it on the repository, so a plugin update reaches every project and `/update` is no longer needed after each one. The repository keeps its state and configuration (the system of record), unlike gstack, which keeps project state in the home folder.
- 2026-10-29: Engine version in `engine/VERSION`, not `plugin.json` (a version there changes how Claude Code detects updates). Projects pin a minimum (`HARNESS_VERSION`), not an exact match, so auto-updates never block a teammate; evidence records the engine version.
- 2026-10-29: Projects installed before 2.0 are migrated by `/odoo-harness:update`; until then the new hooks stand down (the vendored `harness/feature.py` is the marker) and the old per-version plugins stay in the marketplace, deprecated, on their frozen branches.
- 2026-10-30: A task name no longer has to be an Odoo code: work can start before the Odoo task exists, under any name that is safe as a git branch and a file name (letters, digits, `-`, `_`; never a shared branch). `feature rename-task OLD NEW` then renames the features, the local branch and the PROGRESS.md lines. Commits keep the old name (history is not rewritten), so the guide matches a feature's commit without its [task] tag; the evidence stays valid because the fingerprint does not cover the task. The old remote branch and merge request are reported, not removed: a human closes them.
- 2026-10-30: A free task name is refused when a branch of that name already exists locally or on origin, because it may be a shared environment branch (preprod, recette) that the guard does not know; a name with a digit keeps the old behavior, since an Odoo code may already have its branch. Engine 2.1.0: older engines reject free names and tell the user to restore feature_list.json, so a project that uses them needs HARNESS_VERSION=2.1.0 (`/odoo-harness:update`).
- 2026-11-01: Work Rules take three behavior rules from the Karpathy guidelines (github.com/multica-ai/andrej-karpathy-skills), not the plugin itself: state the reading of the feature and ask when it is ambiguous (the loop has no human, so its maker takes the simplest reading and writes it under Known issues instead of blocking, which verify would refuse); write the least code that does the behavior, but reusable by other clients (values that differ between clients come from configuration: an ir.config_parameter setting, a res.company field or an editable data record, never a literal; simplicity means no speculative behavior, not hardcoded values); change only the lines the feature needs. "You own its problems" now means the lines you change and what blocks the feature. The odoo-reviewer checks Assumptions, Simplicity and Reusable (verification already enforces the fourth principle, goal-driven execution).
- 2026-11-03: Dev DB mode (optional, `DEV_DB` in harness.env), superseding the 2026-10-27 test runtime decision for projects that set it: the agent tests where the developer does. One PostgreSQL, the dev stack's, holds the disposable test DB (demo data, unit and integration tests, fresh installs, `init --reset`) and the dev DB (e2e tests); one harness Odoo serves both (dbfilter on the two names). The dev DB is a copy of the client's data that can be restored, so the harness updates it with -u and never creates, drops or resets it; the guard still denies any drop but the test DB's. Conditions: the dev DB must be neutralized (`database.is_neutralized`, checked by init and before every e2e run, so no real e-mail, cron or payment call leaves); e2e tests create their own records with unique names and must pass twice in a row; verify warns when the dev DB was last updated from another branch. The harness Odoo stays separate from the dev Odoo: it runs the agent's code with its own config, restarts without interrupting the developer and mounts the repository read-only. Secrets (dev PostgreSQL password, e2e login) go in the git-ignored `harness/dev.local.env`. User guides replay the e2e tests on the dev DB too: a guide is for the team's developers, so it shows the database they work on (its screenshots hold the client's neutralized data; the PDF stays in the client's repository). Commands on the dev DB use a config without demo data (`without_demo = all`, `with_demo = False` from 19.0), so a dependency that `-u` installs loads none into the client's copy. Without `DEV_DB` nothing changes: the harness keeps its own PostgreSQL. Engine 2.2.0: an older engine ignores `DEV_DB` and runs the e2e tests on the test DB, so a project that sets it needs HARNESS_VERSION=2.2.0 (`/odoo-harness:update`).
- 2026-11-04: Third-party addons (THIRD_PARTY_ADDONS: OCA and other vendors) are no longer read-only, superseding that part of the 2026-10-27 decision: the project's team patches them, so the guard no longer denies their edit. Odoo core, the Enterprise checkout and deployment files stay protected. Verify treats a third-party module changed on the branch like a changed custom module: it is updated (`-u`) and its tests run in L2, its custom dependents are tested too, and in dev DB mode it is updated on the dev DB (and by the guide capture). It is not linted in L1: the house rules are for the project's own code, and vendor code would fail them on lines the patch did not write. Engine 2.3.0: an older engine does not update a patched third-party module, so its views and data are not reloaded and its tests do not run.
- 2026-11-04: Database names (DEV_DB, TEST_DB) are no longer limited to letters, digits and `_`: client copies are named like `stca-sta-22092026-dup`. The only rules left protect data: TEST_DB is never empty nor a path (`init --reset` deletes `filestore/<TEST_DB>`), and `install_template` refuses spaces and shell characters because harness.env is sourced by bash. SQL quotes the names, the dbfilter escapes them, and the guard hook reads a whole name (dots included).
- 2026-11-04: Several developers on one project (docs/design-multi-developer.md): the harness state is split by task, because one shared file per project made every two task branches conflict on it. Each task has `tasks/<task>.json` (its features; written only by `odoo-harness feature`) and `tasks/<task>.md` (its notes), so only the developer on that branch writes them. PROGRESS.md keeps only what concerns the whole project and the harness never writes it; the current state (last commit, test and lint status) moves to the git-ignored `.harness/current-state.md`, being machine state. Feature ids are numbered per task (`F-T2003-1`) so two branches never pick the same id; legacy `F-001` ids stay valid. WIP = 1 holds per checkout and per task: a teammate's in-progress feature, merged into the base, does not block you. `feature add` and `start` check out the task branch, joining a teammate's `origin/<task>` when it exists (fast-forward only) and refusing one that predates the harness. The loop leaves alone tasks whose branch is on GitLab. `init` does not bulk-seed every open task on a multi-developer project: each developer adds a task's features when taking it. `DECISIONS.md merge=union` in `.gitattributes` is a safety net for local merges only (GitLab's merge may ignore it). The ai-workflow commands are not supported alongside the harness: they are being dropped. Engine 3.0.0: `/odoo-harness:update` migrates the old layout once, and must reach the base branch before anyone opens a task branch. It raises HARNESS_VERSION to 3.0.0, and that pin is required: an older engine on a migrated repository does not see tasks/ and would start a new single feature file next to it.
- 2026-11-05: Settings that differ between developers leave the versioned harness.env, superseding where the 2026-11-03 decision put DEV_*: a project worked by several developers cannot share one developer's port, dev stack and dev database in a file pushed to the base branch. harness.env keeps what the whole team shares; the git-ignored `harness/dev.local.env` (the name the secrets already had, so no teammate renames a file) holds ODOO_PORT, DEV_DB, DEV_DB_HOST, DEV_DB_PORT, DEV_DB_USER, DEV_NETWORK, DEV_DATA_DIR and the passwords, and may override ENTERPRISE_DIR, kept shared as the team's workspace layout so a developer without a local file still has Enterprise mounted and guarded. Any other key in the local file is ignored (and reported at session start), so every developer verifies with the same rules. One loader, `hlib.read_settings`, serves Python, the shell scripts (`hlib.py shellenv`, secrets excepted), compose (the settings go into its environment, which wins over `--env-file`) and the hooks. ODOO_PORT defaults to 18069. `odoo-harness init` creates the local file from the plugin's template when missing, only where git ignores it. Engine 3.1.0: `/odoo-harness:update` moves the machine values out of harness.env into the local file of the developer who runs it (a value already set there wins) and raises the pin, since an older engine ignores the local file; once merged, each teammate sets their own port and dev DB mode in their local file. Until then the engine still reads machine values left in harness.env and the session start says to move them.
- 2026-11-06: The lint and e2e tool images are named per machine (`odoo-harness-<tool>:<sha256 of its Dockerfile>`, `pull_policy: never`) instead of per compose project: compose built a private `<project>-e2e` copy per project (1.2 GB unique each, measured). `init` removes the per-project copies of older engines and the shared images of an older recipe, by reference and only the harness's own. A project image with a `VOLUME` beyond `/var/lib/odoo` (the fogits images declare one on the Odoo source, 1.3 GB copied per container) gets a warning, not a failure: the fix is in the image. Engine 3.1.1.
- 2026-11-06: Odoo 16.0 is supported, in the one plugin like the other versions (no `16.0` branch, no deprecated `odoo-harness-16` plugin): `versions.json`, a guide in `skills/odoo/versions/16.0/` checked by `check_skill.py` against the 16.0 source, and the CI matrices. The engine needed no version branch: Odoo 16.0 has `/web/health`, curl, the `database.is_neutralized` flag, `without_demo` and the test-log messages that verify.py parses, all checked in the 16.0 source and image. The 16/17 boundary gets `odoo-version-api` rules both ways, each run over the core of both versions to match nothing where the code is valid: below 17.0, modifiers with record expressions (`invisible="state != 'draft'"`, also set by an inherited view with `<attribute name="invisible">`), `odoo.tools.SQL`, `search_fetch`, `_compute_display_name` without `name_get`, field widgets registered as objects; from 17.0, `attrs`/`states` (on the element or through `<attribute>`). View rules skip `static/` (OWL templates are not views). Rules that judge a whole file are functions (`FILE_RULES`). Odoo 16.0 and 17.0 transpile a JS file only when it starts with `@odoo-module` (18.0 transpiles every file in `static/src`), so the rule `odoo-module-header` covers both (module assets in `static/` only, `static/lib/` excepted), and the 17.0 guide, whose JS examples lacked the comment, got it; it also lost `auth='bearer'`, which arrives in 18.0. Engine 3.2.0: an older engine has neither the 16.0 guide nor its rules, so a 16.0 project pins 3.2.0 (the installer writes the pin).
- 2026-11-06: With the fogits dev stack (`docker-compose/first_build/Dockerfile`), the test runtime is the dev stack's own image and Odoo source, superseding for those projects the 2026-10-27 image built from the project's Dockerfile: the harness built a 2.3 GB copy of what the developer already runs. The installer takes the image of the dev compose file's Odoo service (`evms:odoo`) with `ODOO_DOCKERFILE` empty, and an update moves a project off the `<project>-odoo:local` image an older install built (a name chosen by hand is kept). `init` never builds that image: when it is missing, it prints the `docker build docker-compose/first_build --tag <image>` command for the developer. `ODOO_SOURCE_DIR=../addons` (team layout `~/Project/<client>`, like `ENTERPRISE_DIR`) mounts the dev stack's Odoo source read-only on `/usr/lib/python3/dist-packages/odoo`, so the harness runs the Odoo the developer runs and Docker no longer copies the image's Odoo (1.3 GB) for every container: the VOLUME warning of the 2026-11-06 tool-images decision is removed. Each developer then verifies against their own dev stack's Odoo source, as dev DB mode already tests where the developer works. Engine 3.3.0.
- 2026-11-09: Shared submodules (a GitLab project several projects include, such as `l10n_tn_account` in bpa19 and moveandconnect-19). The project's git saw a submodule only as its pointer, so verify could set `passing` without linting, upgrading or testing a changed shared module, and `gitlab mr` could push a pointer to a commit that existed only on the developer's machine. Now verify diffs inside each checked-out submodule (one level; a nested one, a missing base commit or a changed submodule that is not checked out are red pens), and its modules count as the project's: linted and tested like custom ones when their folder is in CUSTOM_ADDONS, with their dependents. The verify report records the tree of each submodule as tested, committed or not. A task ships in two merge requests merged in this order, as the team works: the submodule's (branch `<task>` of its project, to its `.gitmodules` branch), then the project's, opened as Draft. Once GitLab says the first is merged, `gitlab mr` again pulls that branch into the task branch (pointer on the merged commit, committed and pushed). It drops `Draft:` only when each pointer's tree is the one the task's latest evidence tested, so someone else's merge in between means verifying again. So the project never merges a pointer to a task-branch commit, whatever the submodule's merge mode. The shared project carries its own knowledge files (`CLAUDE.md` with the backward-compatibility rule, `DECISIONS.md`, `ARCHITECTURE.md` with "Projects using it"), from `shared-template/`. They are added by the first task that changes it, in the same commit as its change (`feature verify` gives the command when they are missing; its merge request is refused without them) and named at session start by every project that uses it, with their last decisions only when the current branch changes the submodule: on every other branch they would only take room. Task features and evidence stay in the project where verify ran: a full harness in the shared project would still not test the other projects' modules, and each one's verify does when it moves its pointer. No registry of the projects using it: a section of its ARCHITECTURE.md kept by people. The guard protects `.gitmodules` branches from pushes, `feature add/start` check out the submodule commits the branch records, and `init` refuses an addons submodule that is not checked out. Engine 3.4.0: an older engine does not see the changes inside a submodule.
- 2026-11-09: Documents a project wrote before the harness are adopted, not shadowed: the installer moves Architecture.md, docs/decisions.md, decision.md, claude.md... to the harness name when it is free (reported `renamed`) (git mv when tracked, root and docs/ only, never addon folders) and reports every copy `duplicate` otherwise; init discovery checks their content against the code and corrects what is false. Past decisions are never rewritten: a new dated decision supersedes them, and entries not in `- YYYY-MM-DD:` form are rewritten into it so sessions load them.
- 2026-11-09: The knowledge files of the shared submodules can be added before any task changes them, with `odoo-harness gitlab shared <task>`. This supersedes "the first task that changes it adds them" as the only way. The command opens one merge request per submodule in its own project; the user asked for a branch of the task and a merge request in each. It takes the submodules in a `CUSTOM_ADDONS` folder on `GITLAB_URL`; an OCA mirror or an Odoo checkout on the same GitLab is not shared modules. It runs twice. The first run writes the files in a git-ignored worktree of the submodule's branch tip (`.harness/shared/<path>`) and leaves the developer's checkout untouched. The second run ships them once `ARCHITECTURE.md` is no longer the template: a map nobody filled would tell every project's sessions nothing. Starting from the tip, not the pointer, keeps the merge request to the files alone and maps the code it merges into. The project's pointers are not moved: the files reach a project with its next pointer move, and moving the pointer here would bring others' changes that no verify has tested. Files merged on the branch after a project's pointer count as present (`gitlab mr` no longer asks for them; verify and session start say to rebase), so the project does not write a second copy that would conflict. Engine 3.5.0.
- 2026-11-12: The deprecated per-version plugins (`odoo-harness-17`...`-20`) are removed from the marketplace, superseding "the old per-version plugins stay in the marketplace" (2026-10-29): every project uses `odoo-harness`.
